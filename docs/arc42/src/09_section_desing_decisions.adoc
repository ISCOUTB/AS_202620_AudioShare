# ADR-001: Monolito modular

## Contexto

AudioShare necesita integrar la gestión de salas, la transmisión de audio
y la sincronización de reproducción. Como se trata de un prototipo, se
busca mantener una solución sencilla de desarrollar, probar y desplegar.

Se consideraron diferentes estilos arquitectónicos, entre ellos una
arquitectura por capas, una arquitectura hexagonal y un monolito modular.

## Decisión

Se decidió utilizar un monolito modular para AudioShare.

La aplicación se mantiene como una única unidad de ejecución, pero sus
responsabilidades se separan en módulos independientes.

==== Justificación

El monolito modular permite mantener una estructura clara sin introducir
la complejidad de desplegar y comunicar múltiples servicios.

Además, permite separar las principales responsabilidades del sistema y
facilita las pruebas y el mantenimiento del prototipo.

==== Consecuencias

* El sistema se despliega inicialmente como una única aplicación.
* Las responsabilidades se separan mediante módulos.
* Se facilita la realización de pruebas.
* Se reduce la complejidad inicial de despliegue.
* En el futuro se podrá evaluar separar algún módulo si las necesidades
  de escalabilidad lo justifican.


=== ADR-002: Separación en módulos session, audio y sync

==== Contexto

AudioShare tiene tres responsabilidades principales: gestionar las salas
y participantes, transmitir el audio y mantener sincronizada la
reproducción entre los dispositivos.

==== Decisión

Se dividirá la aplicación en tres módulos principales:

* `session`: gestiona las salas y los participantes.
* `audio`: gestiona las funciones relacionadas con el audio.
* `sync`: gestiona la sincronización de reproducción entre los receptores.

==== Justificación

La separación permite mantener responsabilidades claras y reducir el
acoplamiento entre las diferentes partes del sistema.

También permite que cada módulo pueda evolucionar y probarse de forma
más independiente.

==== Consecuencias

* Cada módulo tendrá una responsabilidad definida.
* Se facilita el mantenimiento del código.
* Las pruebas pueden organizarse según cada responsabilidad.
* Se deberá evitar crear dependencias innecesarias entre módulos.


=== ADR-003: Priorizar la sincronización de audio

==== Contexto

La principal característica de AudioShare es permitir que varios
dispositivos escuchen el mismo audio de forma coordinada.

Por esta razón, la sincronización entre los dispositivos receptores es
un aspecto importante de la arquitectura.

==== Decisión

La sincronización de reproducción se tratará como una preocupación
arquitectónica prioritaria.

Las decisiones relacionadas con la transmisión y reproducción del audio
deberán evaluarse considerando su impacto sobre la sincronización entre
los dispositivos.

==== Justificación

El árbol de utilidad y los escenarios de calidad del proyecto establecen
la sincronización y el rendimiento como aspectos importantes del sistema.

Los escenarios definidos permiten medir el comportamiento de la
sincronización mediante valores concretos de latencia y diferencia de
reproducción.

==== Consecuencias

* Las decisiones de transmisión deberán considerar la latencia.
* La sincronización deberá poder medirse mediante pruebas.
* Los cambios en los módulos `audio` y `sync` deberán evaluarse según su
  impacto en la reproducción coordinada.
